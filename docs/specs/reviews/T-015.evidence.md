## Decisões de implementação para o revisor
1. **Códigos de erro de `page` e `size`:** a spec define `tamanho-maximo` para `size > 100` e diz apenas "400 no campo correspondente" para os demais casos. Usei `formato-invalido` para: `page` negativo ou que não é um inteiro; `size` igual a 0 ou que não é um inteiro; valor acima de `Integer.MAX_VALUE`. Só se aceitam dígitos, então `+1` e `-1` são recusados.
2. **SQL fixo com filtros opcionais:** os filtros usam `CAST(:x AS DATE|VARCHAR) IS NULL OR coluna …`. Não há concatenação de SQL em tempo de execução: o texto é uma constante, montada com *text blocks* na carga da classe, e por isso o FindSecBugs não acusa injeção. A ordem é `ORDER BY data_referencia DESC, id`, a do índice; o `id` é comparado como UUID (bytes sem sinal). O *fake* de teste ordena pelo texto canônico do UUID para reproduzir essa ordem, porque `UUID.compareTo` compara com sinal.
3. **O detalhe recusa qualquer parâmetro de query** (`parametro-desconhecido`). É a mesma regra do histórico, com uma lista de permitidos vazia.
4. **Reúso:** `EntradaDeEstorno.id` (validação do UUID canônico, Q-018) deixou de ser `private` (agora é de pacote) e é usada também no detalhe.
5. **Contrato:** o 404 do detalhe reusa o componente `LancamentoNaoEncontrado` da T-014, cujo exemplo mostra um `instance` de estorno. A estrutura é a mesma; não criei um componente só para mudar o exemplo.
6. **`total` sem transação comum:** como a spec decidiu, a página e a contagem são duas consultas independentes (documentado em `ConsultarLancamentos` e `PaginaDeLancamentos`).
