## Decisões, interpretações e achados (para o autor conferir)
1. **Q-095 (a), com autorização do autor para baixar o builder:** `image.builder` de `0.0.201` para `0.0.213` (publicado em 2026-11-12). A mudança é de uma linha no `pom.xml`.
2. **O achado do Trivy:** `CVE-2026-78661` (HIGH), `golang.org/x/net` v0.61.0, corrigido na 0.62.0, em `layers/paketo-buildpacks_bellsoft-liberica/helper/helper`. Os JARs do projeto deram **0** achados. O log completo foi colado pelo autor; eu não consigo ler logs do GitHub sem login.
3. **A causa é um CVE novo contra uma versão antiga:** o builder 0.0.201 (e todas as imagens que ele gera) traz o `x/net` 0.61.0 no helper do `bellsoft-liberica`; o CVE foi publicado depois e o Trivy atualiza o banco todo dia. Não é efeito da T-045.
4. **A supressão da T-037 foi removida inteira.** A evidência abaixo mostra que os dois helpers cobertos por ela (`ca-certificates` e `spring-boot`) passaram do Go 1.27.2 para o 1.27.3 com o builder novo. O `trivyignore.yaml` ficou com `vulnerabilities: []` e um comentário que explica o histórico e a regra para o próximo achado.
5. **Risco assumido, a confirmar no run:** o Trivy não leu localmente um `trivyignore.yaml` com lista vazia (o Trivy local não é autorizado). O YAML é válido (`vulnerabilities=[]`, conferido com SnakeYAML); o run do `security.yml` no PR confirma se o Trivy aceita o arquivo assim. Se não aceitar, a saída é manter uma entrada de marcação ou tirar o `--ignorefile` do `security.yml` (esse arquivo está fora dos `allowed_paths` desta tarefa).
6. **Um erro meu durante a prova, corrigido:** o primeiro `.env` isolado usou portas acima de 65535 (`69092`, `68090`, `69090`), que não existem, e a stack não subiu. Refiz com portas válidas (`56432`, `56092`, `56090`, `56190`, `56300`) sobre as mesmas imagens já construídas.
7. **O Docker religou sozinho a stack `fluxo-caixa` do autor** (só `postgres`, `kafka`, `prometheus` e `grafana`); eu não a toquei. O `docker cp` e `docker create` usaram contêineres com nome `t047-*`, todos removidos.
