## Decisões, interpretações e achados (para o autor conferir)
1. **Causa raiz da subida lenta dos contêineres (achado importante).** As primeiras execuções mostraram os serviços em contêiner levando 3 a 4 minutos para subir (contra uns 7 s pelo Maven), e a `demo.sh` reprovava na espera pela saúde. O motivo: o `build-image` usava o `paketobuildpacks/builder-noble-java-tiny:latest`, que neste Docker Desktop resolvia para **`linux/arm64`** num daemon `linux/amd64`, então os serviços rodavam sob **emulação** (`docker run` avisava "requested image's platform (linux/arm64) does not match the detected host platform (linux/amd64/v3)"). Um *benchmark* de CPU e de leitura de jar no mesmo Docker foi normal; o mesmo jar num contêiner `eclipse-temurin` comum chegou ao "Tomcat initialized" em 3 s. A correção, em `pom.xml` e nos dois `pom.xml` dos serviços: `<imagePlatform>${image.platform}</imagePlatform>` (padrão `linux/amd64`; perfil `imagem-arm64` ativado em `os.arch=aarch64`) e `<builder>${image.builder}</builder>` com tag fixa `paketobuildpacks/builder-noble-java-tiny:0.0.200` (04 §2.5), mais `pullPolicy IF_NOT_PRESENT`. Resultado: os serviços ficam prontos em cerca de 25 s. Quem já tiver o `builder:latest` arm64 em cache precisa de `docker rmi paketobuildpacks/builder-noble-java-tiny:latest` e das imagens-base `paketobuildpacks/ubuntu-noble-run-tiny` antigas (vale registrar no README se alguém reportar `Image platform mismatch`).
2. **`build-image` intermitente:** antes da correção acima o `build-image` falhava às vezes (`Builder lifecycle 'creator' failed with status code 62`, "failed to fetch base layers: unexpected EOF"), (e imagens parciais no cache). Depois da correção, as construções seguidas deram exit 0 e as imagens saem `linux/amd64` com cerca de 760 MB (o tamanho muda com a plataforma).
3. **Um comando para o passo 3 do README:** a Q-064 diz "compilar e gerar as imagens"; criei o perfil Maven `imagens` (nos dois serviços, goal `build-image-no-fork` na fase `package`) para ser `./mvnw -q install -DskipTests -Pimagens`, em vez de dois comandos. O `spring-boot:build-image` avulso continua funcionando.
4. **Variáveis do compose:** `LANCAMENTOS_PORT` e `CONSOLIDADO_PORT` (e as de gestão, que já existiam) são opcionais no `.env.example`, só para trocar as portas do host. O serviço `dev-keys` roda o `scripts/DevToken.java` num `eclipse-temurin:25.0.1_8-jdk-noble` (tag fixa), só cria o par de chaves se ainda não existir, e os serviços montam `deploy/dev-keys` somente leitura. Imagens dos serviços com `pull_policy: never` (vêm do `build-image`, nunca de um registro).
5. **`demo.sh`:** no rascunho de 168 linhas a data de hoje vinha de `TZ=America/Sao_Paulo date`, que o Git Bash ignora (o dia saía em UTC e errava à noite). Agora "hoje" é o `dataReferencia` devolvido pelo serviço (fuso de negócio, 03 §4.1) e o D-3 sai de aritmética de datas. O `uuidgen` saiu (Q-065): `uuidgen` se existir, senão `/proc/sys/kernel/random/uuid`, senão uma lista gerada de uma vez por um programa Java de arquivo único (a fila fica num arquivo, sem perder estado em subshell). A espera por saúde agora tem limite e é feita também depois de religar o Consolidado (120 s); `--kafka-down` espera até 180 s pela outbox.
6. **Portas do autor:** na primeira tentativa, as portas 8081/8082/9081/9082 estavam ocupadas por serviços do autor rodando pelo Maven (por isso 401: chaves diferentes). Não os toquei. As execuções isoladas usaram `COMPOSE_PROJECT_NAME` próprio e, nas primeiras rodadas, portas alternativas para os serviços (`LANCAMENTOS_PORT`, `CONSOLIDADO_PORT` e as de gestão, que a `demo.sh` aceita por `LANC_URL`, `CONS_URL`, `MGMT_LANC` e `MGMT_CONS`); as rodadas finais, abaixo, rodaram com as portas padrão depois que o autor liberou a máquina.
7. **`jq` instalado no PC do autor com autorização dele** (`winget install --id jqlang.jq`, versão 1.8.2, download do GitHub do jq com hash verificado) para poder validar o caminho real do Windows (Q-065).
8. **`deploy/verify-local.sh`:** sem alteração. Ele só confere Postgres, Kafka e tópicos, que não mudam com o profile `apps`.
9. **`demo.yml`:** não foi executado no GitHub (este ambiente não o acessa); o equivalente local é a sequência abaixo (os mesmos comandos do job, em Linux-like via Git Bash e em PowerShell). O link da execução fica como pendência para o autor depois do *merge*, com `workflow_dispatch`.
