## Achados
| Sev (bloqueante/nota) | Item da rubrica | Descrição | Arquivo:linha |
|---|---|---|---|
| nota | R7/R10 (AC-T006.3) | **O teste "terminou com exit 0" também passa com o contêiner ainda em execução.** `docker compose ps -a --format '{{.ExitCode}}'` devolve `0` para um contêiner em execução: o revisor obteve `0 running` para o `kafka`. Como o `up --wait` considera "*healthy*" um serviço sem *healthcheck* que está rodando, o `verify-local.sh` executado logo depois do `up` pode marcar `✔ kafka-topicos terminou com exit 0` antes de o script de tópicos terminar. No passo 3, o `ps` logo após o `up` ainda mostrava `kafka-topicos running`. Hoje isso não gera falso verde, porque a checagem de partições dos tópicos no fim do script pega a falha real. A lógica vem da T-004 (`init_exit`); a T-006 só renomeou a variável. O README agora afirma que o script "confere se o `kafka-topicos` terminou com exit 0", o que é mais forte do que a verificação faz. Para resolver, exigir `{{.State}} == exited` junto com o exit code, ou usar `docker wait` | `deploy/verify-local.sh:33-34`; `README.md:72` |
| nota | R10 | **O `--remove-orphans` não remove os volumes anônimos do órfão.** A imagem `apache/kafka:3.9.1` declara 3 `VOLUME` (`/etc/kafka/secrets`, `/mnt/shared/config`, `/var/lib/kafka/data`). Ao remover o `kafka-init` órfão, o compose remove o contêiner, mas deixa os 3 volumes anônimos dele, e o `down -v` documentado depois não os alcança, porque o contêiner já não existe. O mesmo vale para o `rm -f` do caso de falha do AC-T006.3. É lixo pequeno e sem dado relevante, mas o README diz que o `down -v` apaga "tudo, inclusive os volumes". Uma frase no README (`docker volume prune`) resolveria | `README.md:70-72` |
