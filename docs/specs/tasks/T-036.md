## Objetivo
Mostrar, **só no ambiente local**, os fluxos reais de autenticação com um IdP padrão (OIDC), sem escrever código de identidade e sem mudar o código dos serviços. O Keycloak faz o papel que o **Cognito** tem na arquitetura-alvo (ADR-010): os dois falam OIDC, e os serviços só validam o JWT de um emissor configurado.

## Escopo: local × nuvem
- **Local (esta tarefa):** Keycloak no profile `auth` do compose, para demonstração.
- **Nuvem (só desenho):** Cognito (ADR-010). Keycloak autogerenciado continua **rejeitado para produção** (ADR-010, "Alternativas rejeitadas"); aqui ele é apenas um substituto local padrão do IdP gerenciado.
- **Testes automatizados, k6 e `scripts/demo.sh` continuam com o `DevToken.java`**: determinísticos e sem dependência do Keycloak.

## Entradas
ADR-007 (validação do JWT, tipos de cliente, *scopes*, `merchant_id`), ADR-010 (Cognito no alvo), `03 §5` (Swagger UI e esquema `bearerAuth`), `03 §6`, `00 §7` (sem front-end), T-013 (validação do JWT nos serviços), Q-008.

## Decisões da tarefa
- **Imagem pinada** do Keycloak (versão estável na data da execução; registrar na evidência), modo de desenvolvimento com importação do *realm* na subida.
- **Realm versionado** em `deploy/keycloak/realm-fluxo-caixa.json`:
  - *Client scopes* `lancamentos:write`, `lancamentos:read`, `consolidado:read`.
  - *Client* público `swagger-ui`: *authorization code* + PKCE, *redirect* restrito às Swagger UIs locais.
  - *Client* confidencial `integrador-demo`: apenas *client credentials*, com os *scopes* mínimos e `merchant_id` fixo por *mapper*.
  - Dois usuários de demonstração (comerciantes A e B) com o atributo `merchant_id` mapeado para o token.
  - *Mapper* de audiência para que `aud` contenha a API (ADR-007).
- **Nenhum segredo no repositório:** senhas dos usuários e o segredo do `integrador-demo` vêm de variáveis do `.env` (substituição na importação do *realm*); `.env.example` traz só valores de exemplo para desenvolvimento.
- **Serviços:** um profile Spring `keycloak` com apenas `spring.security.oauth2.resourceserver.jwt.issuer-uri` (e a audiência esperada) apontando para o Keycloak. Nenhuma linha de código Java muda; sem o profile, o comportamento é o da T-013.
- **Swagger UI:** os YAML *contract-first* ganham um segundo esquema de segurança `oauth2` (*authorization code* + PKCE), usado só com o profile `keycloak`; o `bearerAuth` existente continua.
- **Sem *password grant*** (removido no OAuth 2.1): pessoas entram só pelo *authorization code* + PKCE.

## Saídas
- `deploy/docker-compose.yml` com o serviço `keycloak` no profile `auth` e *healthcheck*.
- `deploy/keycloak/realm-fluxo-caixa.json`.
- `application-keycloak.yml` nos dois serviços.
- Esquema `oauth2` nos dois YAML de OpenAPI.
- `scripts/keycloak-smoke.sh`: obtém token por *client credentials* e chama os dois serviços.
- README: seção "Autenticação: local e nuvem" com a tabela de modos (`DevToken`, Keycloak local, Cognito no alvo) e os comandos.
- `architecture.md §7` e ADR-007 atualizados com o modo Keycloak local.
- `docs/specs/reviews/T-036.evidence.md`.

## Critérios de aceite
- **AC-T036.1** `docker compose --profile auth up -d --wait` deixa o Keycloak saudável com o *realm* importado; sem `--profile auth`, a stack é a mesma de antes.
- **AC-T036.2** Com o profile `keycloak` nos serviços, um token obtido por *client credentials* do `integrador-demo` é aceito nos endpoints dos *scopes* concedidos e recebe **403** num endpoint cujo *scope* não foi concedido (`scripts/keycloak-smoke.sh`, exit 0).
- **AC-T036.3** O `merchant_id` do token isola os dados: o `integrador-demo` não enxerga lançamentos criados para outro comerciante (404).
- **AC-T036.4** Login de pessoa pela Swagger UI com *authorization code* + PKCE funciona para os dois usuários de demonstração (verificação manual com captura na evidência).
- **AC-T036.5** Nenhuma senha, segredo de cliente ou chave privada no Git (gitleaks verde); o `.env.example` deixa claro que os valores são só para desenvolvimento.
- **AC-T036.6** `./mvnw verify`, o k6 e o `scripts/demo.sh` continuam passando sem o Keycloak (seguem com o `DevToken`).
- **AC-T036.7** A documentação deixa explícito que o Keycloak é **só local** e que o IdP do alvo é o Cognito, com a mesma configuração por `issuer-uri`.

## Testes exigidos
`scripts/keycloak-smoke.sh` (AC-T036.2, .3) e a verificação manual do AC-T036.4. Não há teste automatizado novo no `verify`: o comportamento de validação do JWT já é coberto pela T-013 com o `DevToken`.

## Não-objetivos
Serviço de autenticação próprio, cadastro de usuários pela aplicação, Keycloak em produção ou na arquitetura-alvo, MFA, recuperação de senha, front-end, migração de usuários (desenho na T-041).
